## The unresolved item — Table 67/68 vs. Appendix A

This is the finding that showed up first in the Chapter 3 review and then got reinforced twice more (Part 3's review found the same mismatch in the efficiency numbers, and Appendix C explicitly claims both sets of numbers came from "a single workstation," which makes the mismatch harder to explain, not easier). I'm not rewriting this one, because doing so would mean picking a set of numbers to declare "correct" without evidence, which is exactly the kind of thing this whole review has been trying to catch. What I can give you is a clear framework for resolving it yourself.

### The core question

Table 67 (Chapter 3's main results, driving the abstract, RQ1/RQ2/RQ3, and the deployment recommendation) and Appendix A.1–A.4 (which claim to be "the complete retrieval results from the 3-fold cross-validation benchmark described in Chapter 3") report different numbers for the same four models under what's described as the same category-only methodology. One of these is very likely the real, correctly-generated result, and the other is likely stale, from an earlier code version, a different sample, or a partial re-run that never made it back into both places.

### How to find out which is real

1. **Check your benchmark script's output timestamps or git history.** If Table 67 and the appendix tables were generated by the same script at different times, whichever run is more recent (and matches your current codebase) is probably the one to keep.
2. **Re-run the category-only benchmark once, right now, on your current code.** Given the dataset is fixed (5,000 images, seeded 3-fold split per §3.4.1), this should be reproducible. Whatever comes out is your answer, compare it against both Table 67 and Appendix A.1 to see which one it matches (if either).
3. **Check whether the appendix numbers might reflect a different sample size or preprocessing step** that got changed after the appendix was generated but before Table 67 was written, or vice versa. The methodology text in §3.4 should match whichever run is authoritative.

### Once you know the answer, here's what needs to change together

If **Table 67/68 turn out to be correct** and the appendix is stale:
- Regenerate Appendix A.1–A.5 and Table 74 (efficiency) from the same run as Table 67/68.
- No changes needed to the abstract, RQ1–RQ3 answers, or Part 3's Summary of Work, they already use Table 67's numbers correctly.

If **Appendix A turns out to be correct** and Table 67/68 are stale:
- Regenerate Table 67, Table 68, and Figures 42–45 from the appendix's run.
- Recalculate every derived percentage in §3.5–3.7 (5.4%, 7.7%, 8.2%, 92.8%, 26.0%, and all the ×-factors) from the new numbers, they won't be 5.4%/7.7%/8.2% anymore if the underlying mAP values change.
- Update the abstract and the RQ1–RQ3 answers in both Chapter 3 and Part 3 to match.
- Update the deployment recommendation in §3.7.2 if the accuracy-efficiency trade-off conclusion changes.

If **neither matches and a fresh run produces a third set of numbers**:
- Use the fresh run as authoritative throughout, same downstream update list as above.

I'd suggest doing this before any of the other Chapter 3 edits below, since several of them (the RQ2 answer's "3.8× latency increase" framing, the deployment recommendation) are only worth polishing once the underlying numbers are settled.
